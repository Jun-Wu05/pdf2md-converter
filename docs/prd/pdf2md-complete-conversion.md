# PRD：安全厂商 PDF 手册 → 完整 Markdown 转换

> 本 PRD 用于 ai-coding-skills v1.2 流程。UI 模式：**headless**（纯 CLI/库，无可视化 UI），故省略「UI 与设计要求」整章与「状态策略」。
> 词汇遵循 `CONTEXT.md`，架构决策见 `docs/adr/0001-table-restoration-in-python.md`。

---

## 问题陈述

作为安全运营平台使用者，我手上有大量安全厂商（奇安信、深信服、邮件网关、微步、EDR、网神 SecIPS）的 PDF 配置/字段说明手册。这些手册里正文、步骤、字段表混排，且字段表多为**无线框中文表**、列宽极不均、多行表头、跨页续表。

直接用 pdf-inspector 跑 `process_pdf`，正文/标题/列表都正常（R4.15.1 样本 11 页 / 134ms / 6980 字），但落到**字段表**上就错乱：表头重复拆段（R4.15.1 §5.3 被拆成两段各自重发表头）、单元格错位串列（§4.2 字段名串到错误列）、跨页续表被截断、§5.5 出现 CJK 解码乱码（`入网网日目入日非高`）照原样流出。

我无法把这些 Markdown 直接喂给下游 RAG/知识库——字段名和说明对不上，等于丢字段。

## 解决方案

在 pdf-inspector 的 Rust 内核**之上**包一层 Python 后处理，对外只暴露一个公开入口 `convert_pdf_to_markdown(pdf_path) -> str`：

- 内部调 pdf-inspector 的结构化输出（带 X/Y/字体的 TextItems），**不**消费已拍平的 Markdown。
- 在 Python 里对 TextItems 做**表格再检测**：行聚类 → 列对齐推断 → 跨页续表合并 → 表头去重，重建为标准 Markdown 表格。
- 对实在保不住结构的表，按 `CONTEXT.md`「降级表示」兜底（定义列表/逐行平铺），保证文本零丢失。
- 检测到解码乱码时标注 `[疑似解码错误]` 并照留原文，不静默流出。

最终产出一份与原 PDF 语义/结构保真的 Markdown，把 6 份安全厂商手册都能正确处理。

## 用户故事

US-1：作为安全运营使用者，我想要把任意一份安全厂商 PDF 手册转成一份 Markdown，以便直接导入知识库做检索，不用手动抄字段。

US-2：作为安全运营使用者，我想要字段表里的字段名和释义/说明一一对应不错位，以便下游能按「字段名 = 含义」准确建索引。

US-3：作为安全运营使用者，我想要跨页的字段表被合并成一张连续的表，而不是续页重发表头把它拆成两段，以便整张表一次读完。

US-4：作为安全运营使用者，我想要即使某张表结构太乱保不住列对齐，至少字段名和说明成对不丢、按原顺序保留，以便人工核对时不缺内容。

US-5：作为安全运营使用者，我想要正文、步骤、标题层级、列表都原样保留，不被表格后处理误伤，以便 Markdown 整体可读。

US-6：作为安全运营使用者，我想要解码乱码被标注出来（如 `[疑似解码错误]`）而不是悄悄混进正常文本，以便我知道哪段需要人工或 OCR 修复。

US-7：作为研发，我想要这个转换层是一个无外部依赖、可在 conda 环境 `pdf-inspector` 内跑通的 CLI/库，以便交付时不带额外基础设施。

## 实现决策

### convert_pdf_to_markdown 入口

对外唯一公开入口 `convert_pdf_to_markdown(pdf_path: str) -> str`（亦提供 bytes 变体）。内部串联：pdf-inspector 结构化提取 → 表格再检测 → Markdown 重建 → 降级兜底 → 乱码标注。返回完整 Markdown 字符串。这是 ADR-0001「后处理放 Python 层」的对外落点。

### 结构化提取来源

通过 `extract_text_with_positions` 拿到带 `x / y / font / font_size / page` 的 `TextItem` 列表（坐标是表格列对齐推断的依据）；通过 `extract_pages_markdown` 拿到 pdf-inspector 已识别的表格/列布局信号作为辅助。**不**依赖 `process_pdf` 返回的已拍平 Markdown 做表格重建（拍平后行列信息已丢）。字段完备性已在 `.pyi` 确认：`TextItem` 含 x/y/font/font_size/page。

### 行聚类与列对齐推断

按 `page + y` 聚类成行，对每行的 TextItem 按 `x` 排序；用 X 坐标直方图推断列边界（说明列宽、字段名列窄，用直方图谷值定列切点）。多行表头（如 SecIPS 表头分两行）合并为单行表头。这是对 `detect_heuristic` 在中文无线框表上失稳的补位。

### 跨页续表合并与表头去重

检测续页首行是否与上页表头列结构一致；一致则识别为续表，合并行、**不**重发表头。修复 R4.15.1 §5.3 被拆两段的回归。复用 pdf-inspector 已有 continuation row merging 思路，但在 Python 层重做判定以绕开 Rust 内核。

### 降级表示

当列对齐推断置信度不足（列数判定不稳、多行表头无法对齐）时，切到 `CONTEXT.md`「降级表示」：优先定义列表 `字段名 — 释义:类型(示例)`，其次逐行平铺。**绝不**为凑 Markdown 表而丢单元格或错位合并。这是字段表「文本兜底」验收底线的实现出口。

### 解码乱码标注

对结果文本做乱码检测（CJK 解码错误产生的可识别乱码模式，如 R4.15.1 §5.5 的 `入网网日目入日非高`）。命中时在该段前插 `[疑似解码错误]` 标注，原文照留。修复根因（Rust `tounicode.rs`）不在本项目层，但不得静默流出。

### CLI 子命令

提供 `pdf2md-full <pdf_path> [-o out.md]` CLI，封装 `convert_pdf_to_markdown`，便于在 conda 环境内一行跑通任意安全厂商手册。替代当前 `run_pdf2md.py` 这种一次性脚本。

## 测试决策

### convert_pdf2md seam / 文本完整性

测试接缝（seam）定在 `convert_pdf_to_markdown` 公开入口——最高层 seam，喂 6 份安全厂商 PDF fixture，只断言外部行为、不测内部模块。本条断言：转换后 Markdown 字符数 ≥ pdf-inspector 原始提取字数的 98%（允许降级重排造成少量标点变化，但不允许丢正文）。覆盖 US-1、US-5。

### 字段表结构 seam / 字段对齐

喂 R4.15.1 §5.3、EDR、邮件网关、外发说明、微步、SecIPS 六份 fixture，断言：每份的字段表区域输出为标准 Markdown 表，且每行「字段名」列与「释义/说明」列一一对应（用「字段名出现在表头、且每行首列是合法字段名」校验）。覆盖 US-2。

### 跨页续表 seam / 表头不重复

喂 R4.15.1 §5.3（跨页字段表）fixture，断言：续页表头不重复出现、行连续、无半行截断——输出里该表只有一处表头分隔线 `|---|`。覆盖 US-3。

### 降级兜底 seam / 文本零丢失

构造或选一份列对齐保不住的 fixture（如 SecIPS 多行表头），断言：降级输出（定义列表或逐行平铺）中每个原始单元格文本都出现、字段名与释义成对、无串行。覆盖 US-4。

### 乱码标注 seam / 不静默流出

喂 R4.15.1 §5.5 fixture，断言：乱码段前出现 `[疑似解码错误]` 标注，且乱码原文照留（未被吞、未被「修」成别的字）。覆盖 US-6。

### 多厂商回归 seam / 全量跑通

6 份安全厂商 PDF 各跑一次 `convert_pdf_to_markdown`，断言全部不抛异常、产出非空、文本完整性 seam 通过。覆盖 US-1、US-7 的可交付性。

## 范围外

- **不改 pdf-inspector Rust 内核**（见 ADR-0001）——解码乱码根因修复、rect/line 检测增强都不在本项目层。
- **不做 OCR**——pdf-inspector 已分类出 scanned/image-based 的页直接走原始路径，本项目不接 OCR 引擎。
- **不做版面像素级还原**——字体颜色、页眉页脚装饰、列宽像素值都不追求（见 CONTEXT.md「不追求」）。
- **不做 Web/UI 界面**——headless，只交付 CLI + Python 库。
- **不做并发/批量调度**——单文件同步转换，批量由调用方包。

## 补充说明

- **依赖**：仅需 conda 环境 `pdf-inspector` 内已装的 pdf-inspector wheel + Python 标准库；表格再检测不引第三方 ML/布局库（坐标直方图用纯 Python 实现）。
- **风险**：若某厂商 PDF 的 TextItem 坐标缺失或字体异常导致行聚类失败，降级路径必须兜住——这是「文本零丢失」的最后一道闸，测试决策的降级兜底 seam 专门盯这条。
- **迭代节奏**：按 v1.2 垂直切片——先跑通「文本完整性 + 乱码标注」最小切片端到端，再加「字段表结构」，最后「跨页续表 + 降级」，每条切片对应一个 Issue，避免水平切片。
- **开放问题**：6 份 fixture 是否需要先固化「人工校对过的期望 Markdown」作为黄金对照？建议在 `/to-issues` 阶段对「字段表结构 seam」单独建一份黄金片段，其余 seam 用规则断言即可。
